# Text-Extraction Stack (Dignite Vault Parse)

> Since #716 phase 2 the stack is its own module, `modules/vault.parse/` (package prefix `Dignite.Vault.Parse`, module prefix `VaultParse`). It references nothing else in this repo (CI: `etc/scripts/check-module-references.mjs`). Extract consumes it only through the contracts in `Dignite.Vault.Parse.Abstractions`; the host chooses the providers. Config sections (`VisionLlmOcr`, `PdfExtractor`, `OpenXmlExtractor`, `PaddleOcr`, `AzureDocumentIntelligence`) sit at the configuration root and did not change with the rename.

> Carried over from CLAUDE.md, auto-loaded when editing text-extraction / OCR / Markdown-provider code. CLAUDE.md states the egress side only: `Document.Markdown` is the only text field.

## Text-extraction capability stack (three-layer contract + multiple providers) — the core pluggable point

- **`Dignite.Vault.Parse.Abstractions`** — the contracts a consumer of extracted text depends on: `ITextExtractor`, `TextExtractionContext`, `TextExtractionResult`, `NativePayload`, `ImageOcrMarkup` (namespace `Dignite.Vault.Parse`). Volo.Abp.Core only; Extract's `Application` references this project and nothing else from Parse
- **`Dignite.Vault.Parse`** — orchestrator + the default `ITextExtractor` implementation (`DefaultTextExtractor`: dispatch by file extension — images go to OCR; everything else goes to the matching Markdown provider, selected per file across coexisting providers by `CanHandle(ext)` + `Priority`, with whole-page OCR fallback when a PDF yields no meaningful text layer). Declares the `IMarkdownTextProvider` side-contract within the same project
- **`Dignite.Vault.Parse.Ocr`** — the minimal contract layer on the OCR-provider implementation side (`IOcrProvider` / `OcrOptions` / `OcrResult`; an OCR provider returns Markdown). Third-party OCR integrations reference only this project and see neither the orchestrator nor the `IMarkdownTextProvider` side-contract
- **OCR provider implementations**: `Dignite.Vault.Parse.Ocr.VisionLlm` (Host's current default, #259: a multimodal vision LLM transcribes photos / thermal receipts / image-type PDFs, reusing the keyed vision `IChatClient` registered by the host; PDFs are rasterized page by page via PDFium + SkiaSharp; depends only on the `Dignite.Vault.Parse.Ocr` contract layer), `Dignite.Vault.Parse.Ocr.PaddleOcr` (local sidecar, PP-StructureV3 runs fine on CPU, outputs Markdown), and `Dignite.Vault.Parse.Ocr.AzureDocumentIntelligence` (cloud option, high accuracy); `IOcrProvider` is mutually exclusive — the Host enables exactly one of the three, and switching requires syncing both `[DependsOn]` and the `.csproj ProjectReference` (when the switch involves VisionLlm, also sync the host `ConfigureAI` keyed vision `IChatClient` registration)
- **Markdown provider implementations (coexist, dispatched per file by extension)**:
  - `Dignite.Vault.Parse.Pdf` (`PdfExtractor`, PdfPig) — owns `.pdf`; extracts the digital text layer **and** embedded raster images, transcribing each image through the **host-selected `IOcrProvider`** (transcription only, no keyed Vision `IChatClient` at this layer, no new LLM call site — reachable because the module references `Parse` → `Ocr`) and **inlining** the transcription into the Markdown at the image's reading position (#301). A PDF with no text layer returns empty so the orchestrator's whole-page OCR fallback owns it (no double OCR). Vector-only graphics are an accepted blind spot; dropped/undecodable images / truncated figure OCR / cap hits trip the #268 completeness signal. Figure output is **inline-into-Markdown only** — `TextExtractionResult` is unchanged (no `Figures` field)
  - `Dignite.Vault.Parse.ElBrunoMarkItDown` (based on ElBruno.MarkItDotNet) — the **catch-all fallback** (`CanHandle` always true, `MarkdownProviderPriorities.Fallback`), covering Word/HTML/plain-text/CSV/RTF/EPUB and `.pdf` when the Pdf module is not installed. **Byte-stream text formats are transcoded to UTF-8 first** (`TextEncodingNormalizer`, #493): ElBruno's `CsvConverter` / `PlainTextConverter` decode via `new StreamReader(stream, null, detectEncodingFromByteOrderMarks: true, …)` — UTF-8 plus BOM sniffing and nothing else — so a no-BOM CP932 CSV (what Excel on Japanese Windows exports) decoded entirely to U+FFFD, and until #660 added re-parse that garbage was unrepairable. The shim covers `.csv` / `.tsv` / `.txt` only (OpenXML declares its encoding in-band; PDF carries per-font encodings): BOM-bearing or strict-UTF-8 bytes pass through untouched, anything else is decoded through a detected legacy codepage (`UTF.Unknown`, confidence ≥ 0.5) or the hardcoded CP932 fallback, then re-encoded as UTF-8 with a BOM. **Decoding must never throw** — an undetectable charset still has to yield Markdown, because a failed parse run is retried by the background job and would never succeed
- **The asymmetry with OCR providers is deliberate** — Markdown providers **coexist and dispatch per file by extension** (each self-declares `CanHandle(ext)` + `Priority`; ElBruno is the catch-all, so omitting a specialized module degrades that extension gracefully), whereas `IOcrProvider` is **host-selected and mutually exclusive** (exactly one enabled via `DependsOn`). The Markdown-provider contract stays close to the orchestrator (tightly coupled); OCR providers are more likely third-party (cloud services / local sidecars), so their separate thin contract layer gives them a stable boundary

## Text-extraction provenance + native payload archiving (#210)

A text-extraction provider's **native output** (bbox / table cells / text-span anchors / confidence / region types and other out-of-band spatial signals) is an **unreliable after-the-fact derivation** (provider version drift → a re-run's bbox may not align with the Markdown already stored/chunked at the time); the only way to get aligned raw material is to **capture it together with the Markdown at extraction time**. Dignite Vault Extract captures and archives it at the channel layer accordingly, holding the boundary strictly:

- **Native payload → blob, not into the DB**: `NativePayload` (`Content` + `ContentType` + `SchemaName`) hangs on the transport `TextExtractionResult`; the OCR provider passes it via flat `OcrResult` fields (`NativePayloadContent` / `NativePayloadContentType` / `NativePayloadSchemaName`), mapped by `DefaultTextExtractor` (the Ocr project does not reference Abstractions); pure text→Markdown providers (ElBruno/MarkItDown) have no spatial model and leave it `null`. The text-extraction job archives it into `IBlobContainer<ExtractDocumentContainer>` under the **stable per-document key** `extraction-native/{documentId}` (re-extraction overwrites, one archive blob per document, no orphans). **The `Document` text payload is still only `Markdown`** — raw bbox is **never** stuffed back into the Markdown string, nor relationalized into the DB.
- **`Document.ExtractionMetadata`** (`DocumentParseMetadata?`, a Domain typed value object → JSON column, going through `AbpJsonValueConverter` — the #206 pattern for a JSON-like payload with no per-column query requirement) — stores **minimal provenance**: `ProviderName?` (the winning provider family name) + `NativePayloadManifest?` (`BlobName` / `ContentType` / `SizeBytes` / `Sha256` / `SchemaName`). **No** `Dictionary<string,object>` bag (#206 principle). No first-class `ExtractionProviderName` column, no path / step chain (zero consumption, cut in review). **Plus an extraction-completeness quality signal** (`IsComplete` + `IncompleteReason?`, #268, optional constructor parameters → old JSON missing the fields defaults to complete) — unlike provenance, this **is exposed at the egress** (see next bullet). Providers report it via the flat `IsComplete` / `IncompleteReason` fields on `OcrResult` / `TextExtractionResult` (set false on VLM truncation / guard hit / PDF page loss; providers that do not set this signal default to true).
- **Archiving fails open**: no payload / over the limit (`DocumentConsts.MaxNativePayloadArchiveBytes`, default 16 MiB) / blob write failure → log a warning, set the manifest to null, **and text extraction still succeeds** — an auxiliary audit blob must never break the main Markdown pipeline.
- **The egress does not expose provenance, but does expose the completeness quality signal**: the REST `DocumentDto` and MCP egress **expose none** of the internal provenance fields such as ExtractionMetadata / BlobName / ProviderName (without a download endpoint a payload summary is not actionable; BlobName is an internal storage key). **Exception**: extraction completeness is a downstream-actionable **quality signal** (not provenance) — the REST `DocumentDto` exposes `ExtractionIsComplete` + `ExtractionIncompleteReason?` (#268, projected from `ExtractionMetadata` by `DocumentAppService.MapToDtoAsync`, null metadata → complete); downstream decides on its own whether to accept / degrade / route to manual review, and the channel layer does not intercept on the downstream's behalf (it does not gate Ready). On permanent deletion, the archive blob is deleted together per the manifest's `BlobName`.
- **`Document.Language` persisted**: writes `TextExtractionResult.DetectedLanguage` via `Document.SetLanguage(...)`, ending the previously write-never dead field.
- **No Layer 3 this round** (normalized `PageBlocks` / anchors / citation) — raw bbox stays in the blob and stops there.

## How providers produce Markdown today (transport / provider layer)

> CLAUDE.md states the egress side: `Document.Markdown` is the only text field. This section describes the provider side as it is built today.

- **Every provider returns Markdown**: `ITextExtractor` / `IMarkdownTextProvider` / `IOcrProvider` have one text output and no plain-text path, so classification, field extraction and downstream chunkers all consume a single format
  - **For structured documents** (contracts / policies / reports / CSV / titled DOCX / PP-StructureV3 / Azure DI prebuilt-layout) — headings, tables, and lists are **real signals** for downstream chunking and LLM understanding; exploit them fully
  - **For unstructured content** (loose OCR paragraphs / plain txt / PP-OCRv4 line-level output / single-sentence notes) — Markdown is a **container naming**, **not** a signal gain; keeping the Markdown path is only so that the downstream chunker / built-in LLM classification / custom field extraction consume one single format. Be honest about this; do not dress up flat paragraphs as "also Markdown signal"
  - **The provider does the wrapping** — `OcrResult` / `TextExtractionResult` have no RawText field. A provider whose engine returns plain text wraps it into flat Markdown itself (e.g. `string.Join("\n\n", paragraphs)`), so the orchestrator never sees a plain-text fallback
- **Prompt expression**: internal LLM system prompts explicitly state "the input is Markdown", letting the model exploit structural markup as a semantic signal

**Markdown-first is an engineering default, not a principle.** Out-of-band signals (coordinates / confidence / page metadata / form key-value structure / stamp position) are a separate question from the text payload. Today none is modelled beyond the archived native payload (#210 above).

**Direction (2026-11-11).** `Microsoft.Extensions.DocumentExtraction` (experimental in dotnet/extensions 11.0.0) has the same positioning as Parse's contracts: an engine-neutral extraction client that returns a structured element tree with page and region references. The plan is to rebuild Parse on it once it leaves experimental status, with no adapter layer between the two. Three things Parse relies on that it lacks (a failed-page signal, a durable native result, a language hint) were raised upstream in dotnet/extensions#7587.

## Re-extraction policy: per-document re-parse (#660), no batch re-OCR

`Document.Markdown` is written **once by the first parse** — `SetMarkdown` throws `MarkdownIsImmutable` once set. After that it changes through exactly two paths: an operator correction (`CorrectMarkdown`, #555, Markdown only) and a **re-parse** (`ReplaceParseOutput`, #660), which replaces every parse output together.

- **Re-parse** — `DocumentAppService.ReparseAsync`, the detail page's "重新解析": re-runs text extraction from the stored original file, then LLM classification and its normal cascade, as for a fresh upload. It replaces Markdown / Title / Language / ExtractionMetadata as one unit, withdraws every sub-document split from the old Markdown together with its ledger rows (`SubDocumentRetractor.RetractAllAsync`, see `sub-document-segmentation.md`), and always re-runs classification, even over an operator-confirmed or upload-declared (#623) type. It is refused on a sub-document (no file of its own; re-parse the parent). Its Complete phase is one transaction and queues classification **before** completing its own run, so the document never derives Ready in between.
- **The mode travels in the job args** (`DocumentParseJobArgs.IsReparse`), decided by whoever queues the run — `ReparseAsync`, or `RetryPipelineAsync` for a failed text-extraction run on a document that already has Markdown. A redelivered first-parse job therefore still fails on `MarkdownIsImmutable`; never infer the mode from the document's state inside the job.
- **Why it exists — #660 reversed the earlier "no per-document re-OCR" rule.** "Digital-born extraction is deterministic" holds only within one version: a fixed parser bug (#493's CP932 CSVs) left every document parsed before the fix broken. A truncated or incomplete OCR on one document is a specific defect a re-run can fix, not an undirected resample. And an operator can bring a document that matters up to a changed host OCR configuration.
- **Drift is announced, not forbidden.** The old objection was Markdown changing *silently* under consumers that derived chunks or records from it. A re-parse re-publishes `DocumentTextExtractedEto`, each withdrawn sub-document fires `DocumentDeletedEto`, and classification re-fires its own events, so downstream rebuilds from the later `EventTime`.
- **Not built**: **batch** re-OCR over stored blobs (#396 was closed over the blast radius and cost of a blanket re-run after a config change), and customer-facing OCR configuration (provider choice is host deployment configuration). Re-upload stays the path for a genuinely different source file.
